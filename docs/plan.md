# InterReview Final Plan

> 대상: Codex / Claude Code  
> 기준: GitHub migration 이후 현재 저장소  
> 목표: **InterReview를 2개 Track으로 단순화하여 최종 시연 가능한 형태로 완성한다.**

---

# 1. 최종 방향

InterReview는 아래 두 기능으로 구성한다.

```text
Track A. 자소서 첨삭
Track B. 발표/면접 연습
```

두 Track은 서로 독립적으로 사용할 수 있지만,
Track A에서 분석한 자소서를 Track B의 질문 생성에도 사용할 수 있도록 연결한다.

---

# 2. Track A — 자소서 첨삭

## 목표

사용자가 입력한 자기소개서에서
**면접에서 약점이 될 수 있는 주장·경험을 찾아내고 예상 질문을 생성한다.**

핵심 분석은 LLM API에 맡긴다.

```text
자기소개서
   ↓
LLM
   ↓
주장 / 경험 분리
   ↓
경험별 위험도 분석
   ↓
약점 및 공격받을 수 있는 지점 탐색
   ↓
예상 면접 질문 생성
```

## LLM이 수행할 작업

1. 자기소개서 문장을 `주장`과 `경험`으로 분리
2. 경험 단위로 면접관이 파고들 수 있는 약점 추출
3. 약점별 예상 질문 생성

예시 출력:

```json
{
  "experiences": [
    {
      "experience": "AI 면접 시스템 개발",
      "weaknesses": [
        "팀 내 개인 기여도가 드러나지 않음",
        "성능 개선 결과가 정량적으로 제시되지 않음"
      ],
      "expected_questions": [
        "프로젝트에서 본인이 직접 담당한 부분은 무엇인가요?",
        "성능을 개선했다고 했는데 어떤 지표가 얼마나 개선되었나요?"
      ]
    }
  ]
}
```


## UI

최소 화면:

```text
자기소개서 입력
→ 분석하기
→ 약점
→ 예상 질문
```

가능하면 위험도가 높은 경험부터 정렬한다.

---

# 3. Track B — 발표/면접 연습

## 목표

자기소개서와 지원자 정보를 기반으로 질문을 개인화하고,
실제 답변 중 **시선과 말투를 측정하여 그대로 보여주고 피드백한다.**

시선·음성 지표에는 점수를 부여하지 않는다.

```text
자기소개서 / 프로필
      ↓
질문은행
      ↓
항목별 랜덤 선택
      ↓
LLM 질문 개인화
      ↓
실제 답변
   ├─ 시선 분석
   ├─ 음성 분석
   └─ STT 답변
          ↓
      LLM 내용 확인
```

---

# 4. 질문 생성 방식

## 4.1 질문은행

기존 ICT 질문은행을 사용한다.

질문은 먼저 항목별로 분리한다.

예:

```text
자기소개·이력
가치관·성향
직무·기술
문제 해결
협업·조직생활
지원동기·직무몰입
```

한 번의 면접에서는 각 항목에서 질문을 랜덤으로 선택한다.

```text
질문은행
→ 항목별 필터링
→ 항목별 Random Pick
→ LLM 개인화
```

질문은행 전체를 LLM에게 넘기지 않는다.

---

## 4.2 질문 개인화

LLM API 입력:

```text
자기소개서
지원 직무
기술 스택
프로젝트 경험
선택된 원본 질문
```

LLM 출력:

```text
개인화된 질문 한 문장
```

규칙:

- 원본 질문 의도를 유지한다.
- 자기소개서에 없는 경험을 만들지 않는다.
- 답변을 생성하지 않는다.
- 설명을 붙이지 않는다.
- 한 문장 질문만 반환한다.

실패 시:

```text
개인화 재시도 1회
→ 실패하면 원본 질문 사용
```

---

# 5. 면접 진행

질문을 순차적으로 보여준다.

```text
질문 표시
→ 녹화/녹음 시작
→ 답변
→ 답변 종료
→ Vision / Audio / STT 처리
→ 다음 질문
```

기존 장치 확인 및 면접 UI가 있으면 그대로 재사용한다.

---

# 6. 시선 분석

## 목적

시선을 채점하지 않고 **사용자가 자신의 시선 패턴을 직접 확인할 수 있도록 한다.**

기존 MediaPipe Face Landmarker 기반 구현을 유지한다.

최소 출력:

```text
시선 Heatmap
평균 시선 위치
중앙 대비 시선 표준편차
유효 시선 프레임 비율
```

핵심 결과는 Heatmap이다.

```text
프레임별 시선 좌표
→ 누적
→ Heatmap
```

가능하면 중앙 기준에서 얼마나 흔들렸는지를 표준편차로 함께 출력한다.

예:

```json
{
  "mean_gaze_x": 0.03,
  "mean_gaze_y": -0.02,
  "gaze_std_x": 0.11,
  "gaze_std_y": 0.09,
  "valid_gaze_ratio": 0.92
}
```

**시선 점수는 만들지 않는다.**

---

# 7. 음성 분석

## 목적

음성 역시 채점하지 않고 실제 측정값을 보여준다.

최소 출력:

```text
총 답변 시간
실제 발화 시간
말의 빠르기
일정 시간 이상 긴 무음 횟수
```

## 기준 참고값

ICT 데이터 분석에서 확인한 값을 참고 정보로 사용할 수 있다.

```text
평균 답변 길이: 약 131어절
평균 답변 시간: 약 90초
상한 참고: 약 120초
```

단, 이 값을 이용해 점수를 만들지 않는다.

예:

```text
발화 속도: 126어절/분
총 답변 시간: 87.4초
2초 이상 긴 무음: 3회
```

---

# 8. 무음 구간

STT word timestamp 또는 audio VAD를 이용한다.

최소 계산:

```text
silence_duration_sec
silence_ratio
long_pause_count
max_pause_sec
```

긴 무음 기준은 config로 둔다.

예:

```text
LONG_PAUSE_SEC = 2.0
```

UI에서는 가공된 점수가 아니라 측정값을 그대로 출력한다.

---

# 9. STT

녹음 종료 후 STT를 수행한다.

권장 흐름:

```text
브라우저 녹음
→ WAV 16 kHz mono
→ local STT
→ transcript
→ word timestamp
```

기존 STT 구현이 있다면 재사용한다.

STT 모델은 질문마다 다시 로딩하지 않는다.

---

# 10. 답변 내용 확인

## 목표

답변의 내용 평가는 복잡한 자체 룰 엔진을 만들지 않는다.

LLM API에 다음을 전달한다.

```text
자기소개서
현재 질문
사용자 답변 transcript
```

LLM에게 묻는다.

```text
질문에 올바르게 답변했는가?
```

권장 JSON:

```json
{
  "answer_status": "good",
  "reason": "질문에서 요구한 프로젝트 문제와 본인의 해결 행동을 모두 설명했다.",
  "missing_points": [],
  "follow_up_question": "해결 결과를 수치로 설명할 수 있나요?"
}
```

상태는 단순하게 유지한다.

```text
good
partial
off_topic
insufficient
```

여기서도 별도 숫자 점수는 만들지 않는다.


---

## Phase 1 — Track A 자소서 분석

구현:

```text
자소서 입력
→ LLM 분석 API
→ 주장/경험 분리
→ 약점
→ 예상 질문
→ 결과 UI
```

완료 기준:

- 하나의 자기소개서를 넣으면 경험별 분석 결과가 JSON으로 나온다.
- 위험도 순으로 확인할 수 있다.
- 예상 면접 질문이 생성된다.

---

## Phase 2 — 개인화 질문

```text
자소서 + 프로필 + 질문은행에서 랜덤 선택한 질문
→ LLM
→ 개인화 질문 한 문장
```

완료 기준:

- 원문 의도 유지
- 프로필 없는 사실 생성 금지
- 실패 시 원문 fallback

---

## Phase 3 — Audio + STT

구현/정리:

```text
질문별 녹음
WAV 저장/처리
STT
word timestamp
발화시간
발화속도
긴 무음 count
```

완료 기준:

- 실제 브라우저 답변으로 모든 값이 생성된다.

---

## Phase 4 — Vision

기존 구현 안정화:

```text
Face Landmarker
→ 시선 좌표
→ 누적 Heatmap
→ 평균
→ 중앙 대비 표준편차
```

완료 기준:

- 질문별 Heatmap이 정상 생성된다.
- 카메라 preview 좌우반전 때문에 분석 좌표가 뒤집히지 않는다.

---

## Phase 5 — 답변 내용 LLM 평가

```text
자소서
+ 질문
+ transcript
→ LLM
→ good / partial / off_topic / insufficient
```

추가:

```text
reason
missing_points
follow_up_question
```

완료 기준:

- 숫자 점수 없이 내용 피드백이 생성된다.

---

## Phase 6 — 결과 화면 통합

질문별로:

```text
내용 피드백
음성 수치
시선 Heatmap
```

을 한 화면에 묶는다.

전체 세션 결과도 제공한다.

---

## Phase 7 — E2E 테스트

최종 시나리오:

```text
자소서 입력
→ 자소서 약점 분석
→ 면접 시작
→ 질문은행 Random Pick
→ 질문 개인화
→ 답변
→ STT
→ 시선/음성 feature
→ LLM 내용 확인
→ 결과 화면
```

처음부터 끝까지 crash 없이 동작해야 한다.

# 14. 코드 원칙

1. 현재 저장소 구조를 우선한다.
2. 불필요한 대규모 refactor를 하지 않는다.
3. LLM prompt와 API 호출 코드를 UI에서 분리한다.
4. Vision/Audio feature 계산도 UI 코드와 분리한다.
5. API key는 `.env`에서 읽는다.
6. LLM JSON은 validation한다.
7. LLM 실패 시 전체 면접이 종료되지 않도록 fallback한다.
8. 질문마다 모델을 새로 load하지 않는다.
9. raw audio/video는 불필요하게 영구 저장하지 않는다.

# 16. 최종 Definition of Done

## Track A

- [ ] 자기소개서를 입력할 수 있다.
- [ ] 주장과 경험을 LLM이 분리한다.
- [ ] 경험별 위험도를 반환한다.
- [ ] 약점을 반환한다.
- [ ] 예상 질문을 반환한다.

## Track B

- [ ] 항목별 Random Pick이 동작한다.
- [ ] 질문이 자소서/프로필 기반으로 개인화된다.
- [ ] 개인화 실패 시 원문 질문을 사용한다.
- [ ] 브라우저에서 카메라/마이크가 동작한다.
- [ ] 질문별 STT가 동작한다.
- [ ] 발화 속도가 출력된다.
- [ ] 답변/발화 시간이 출력된다.
- [ ] 긴 무음 횟수가 출력된다.
- [ ] 시선 Heatmap이 출력된다.
- [ ] 시선 표준편차가 출력된다.
- [ ] LLM이 답변 내용의 적합성을 판단한다.
- [ ] Vision/Audio에는 점수를 부여하지 않는다.
- [ ] 처음부터 결과 화면까지 E2E로 동작한다.

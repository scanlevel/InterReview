# InterReview Final Plan

> 원본: 사용자가 제공한 Plan (1).md
> 문서 기준일: 2026-08-21
> 목표: InterReview를 Track A(자소서 첨삭)와 Track B(발표·면접 연습)로 단순화해 최종 시연 가능한 형태로 완성한다.

이 문서는 사용자 제공 계획을 현재 저장소와 동기화한 공식 계획이다. 이후 결정된 사항은 원본 계획보다 우선한다.

- 추가 질문(follow-up question)은 생성하거나 표시하지 않는다.
- 숫자 점수·감점·종합 점수는 만들지 않는다.
- 답변 내용은 상태·이유·빠진 내용으로, 시선·음성은 측정값 그대로 제공한다.
- 이번 구현·커밋의 주 범위는 Track B다. Track A는 별도 작업이다.

---

## 1. 최종 방향

~~~text
Track A. 자소서 첨삭
Track B. 발표/면접 연습
~~~

두 Track은 독립적으로 사용할 수 있다. Track A에서 분석한 자기소개서 정보는 Track B 질문 개인화에 연결할 수 있다.

---

## 2. Track A — 자소서 첨삭

### 목표

사용자의 자기소개서에서 면접에서 약점이 될 수 있는 주장과 경험을 찾고, 경험별 예상 질문을 생성한다.

~~~text
자기소개서
   ↓
LLM
   ↓
주장 / 경험 분리
   ↓
경험별 약점 분석
   ↓
예상 질문 생성
~~~

최소 UI는 다음과 같다.

~~~text
자기소개서 입력 → 분석하기 → 약점 → 예상 질문
~~~

위 기능은 이번 Track B 커밋에 포함하지 않는다.

---

## 3. Track B — 발표/면접 연습

### 목표

자기소개서와 지원자 정보를 기반으로 질문을 개인화하고, 답변 중 시선과 음성을 채점하지 않고 측정해 그대로 보여준다. 답변 내용은 LLM이 상태·이유·빠진 내용만 확인한다.

~~~text
자기소개서 / 프로필
      ↓
질문은행
      ↓
항목별 Random Pick
      ↓
LLM 질문 개인화
      ↓
실제 답변
   ├─ 시선 측정
   ├─ 음성/VAD 측정
   └─ 기존 CLOVA STT
          ↓
      LLM 내용 확인
~~~

---

## 4. 질문 생성 방식

### 4.1 질문은행

기존 ICT 질문은행을 항목별로 분리해 사용한다.

~~~text
자기소개·이력
가치관·성향
직무·기술
문제 해결
협업·조직생활
지원동기·직무몰입
~~~

한 번의 면접에서는 각 항목에서 질문을 하나씩 무작위 선택하고 중복을 방지한다.

~~~text
질문은행 → 항목별 필터링 → 항목별 Random Pick → LLM 개인화
~~~

질문은행 전체를 LLM에 넘기지 않는다. 질문은행 데이터는 애플리케이션 로직과 별도로 관리하며, 이번 코드 커밋은 질문은행 데이터 자체를 변경하지 않는다.

### 4.2 질문 개인화

LLM 입력:

~~~text
자기소개서
지원 직무
기술 스택
프로젝트 경험
선택된 원본 질문
~~~

LLM 출력은 개인화된 질문 한 문장이다.

규칙:

- 원본 질문 의도를 유지한다.
- 자기소개서·프로필에 없는 경험을 만들지 않는다.
- 답변을 생성하지 않는다.
- 설명을 붙이지 않는다.
- 한 문장 질문만 반환한다.

LLM 호출 실패나 키 미설정 시 선택된 원본 질문을 사용한다.

---

## 5. 면접 진행

~~~text
질문 표시
→ 녹화/녹음 시작
→ 답변
→ 답변 종료
→ Vision / Audio / STT 처리
→ 다음 질문
~~~

기존 장치 선택, 카메라 미리보기, 마이크 확인, 5점 시선 캘리브레이션, 질문별 면접 상태 흐름은 재사용한다.

---

## 6. 시선 분석

### 목적

시선을 채점하지 않고 사용자가 자신의 시선 패턴을 직접 확인할 수 있도록 한다. 기존 MediaPipe Face Landmarker 기반 브라우저 구현을 유지한다.

질문별 출력:

~~~text
시선 Heatmap
평균 시선 위치
중앙 대비 x/y 표준편차
유효 시선 프레임 비율
얼굴 검출 프레임 비율
~~~

~~~text
프레임별 시선 좌표 → 누적 → 12×8 Heatmap
~~~

예시:

~~~json
{
  "mean_gaze_x": 0.03,
  "mean_gaze_y": -0.02,
  "gaze_std_x": 0.11,
  "gaze_std_y": 0.09,
  "valid_gaze_ratio": 0.92
}
~~~

시선 비율·평균·표준편차는 측정값이며 점수로 변환하지 않는다.

---

## 7. 음성 분석

음성도 채점하지 않고 실제 측정값을 보여준다.

질문별 출력:

~~~text
총 답변 시간
실제 발화 시간
발화 속도(어절/분)
무음 시간 및 비율
긴 무음 횟수
최대 무음 시간
~~~

ICT 데이터 분석 참고값은 참고 정보로만 표시한다.

~~~text
평균 답변 길이: 약 131어절
평균 답변 시간: 약 90초
상한 참고: 약 120초
~~~

이 값으로 우열·감점·점수를 만들지 않는다.

---

## 8. 무음 구간

브라우저에서 VAD를 계산한다. 현재 구현 기준은 16kHz mono WAV, 20ms RMS 프레임, VAD_RMS_THRESHOLD = 0.015다.

~~~text
silence_duration_sec
silence_ratio
long_pause_count
max_pause_sec
~~~

긴 무음 기준은 LONG_PAUSE_SEC = 2.0이다. 발화 속도는 STT transcript의 어절 수를 실제 발화 시간으로 나눠 계산한다.

UI에서는 가공된 점수가 아니라 측정값을 그대로 출력한다.

---

## 9. STT

기존 CLOVA Speech 프록시를 재사용한다.

~~~text
브라우저 녹음
→ WAV 16kHz mono
→ FastAPI /stt
→ CLOVA Speech /recognizer/upload
→ transcript
~~~

API 키는 백엔드 .env에서만 읽는다. STT가 실패해도 면접 전체를 중단하지 않고 상태와 빈 transcript를 결과에 남긴다.

---

## 10. 답변 내용 확인

복잡한 자체 점수 엔진을 만들지 않는다. LLM에 자기소개서·프로필, 현재 질문, 사용자 transcript를 전달해 질문에 대한 답변 상태만 확인한다.

응답 JSON:

~~~json
{
  "answer_status": "good",
  "reason": "질문에서 요구한 프로젝트 문제와 본인의 해결 행동을 설명했다.",
  "missing_points": []
}
~~~

상태는 다음 네 가지로 고정한다.

~~~text
good
partial
off_topic
insufficient
~~~

follow_up_question은 사용하지 않는다. 숫자 점수도 만들지 않는다.

## 11. 최종 결과 화면

질문 하나에 대해 다음을 보여준다.

~~~text
질문
답변 transcript

[내용]
- 답변 상태
- LLM 판단 이유
- 빠진 내용

[음성]
- 총 답변 시간
- 실제 발화 시간
- 발화 속도
- 무음 시간/비율
- 긴 무음 횟수

[시선]
- Heatmap
- 평균 시선 위치
- 시선 표준편차
- 유효 프레임 비율
~~~

전체 면접 종료 후에는 질문별 결과와 함께 다음 세션 요약을 한 화면에서 확인한다.

~~~text
ICT 참고 평균 답변시간·답변 어절
이번 세션 평균 총 답변시간
이번 세션 평균 실제 발화시간
이번 세션 평균 무음시간·무음비율
이번 세션 평균 긴 무음 횟수
이번 세션 평균 얼굴 검출·유효 시선·정면 응시 비율
이번 세션 평균 시선 위치·표준편차
~~~

참고값과 세션값은 비교 문장이나 우열 표현 없이 있는 그대로 표시한다.

## 13. 구현 순서 및 현재 상태

### Phase 0 — 현재 코드 확인

이미 구현된 기능은 재작성하지 않고 기존 코드를 연결·수정한다.

### Phase 1 — Track A 자소서 분석

~~~text
자소서 입력 → LLM 분석 API → 주장/경험 분리 → 약점 → 예상 질문 → 결과 UI
~~~

상태: 별도 작업. 이번 Track B 커밋 범위에 포함하지 않는다.

### Phase 2 — Track B 개인화 질문

~~~text
자소서 + 프로필 + 질문은행 Random Pick
→ LLM
→ 개인화 질문 한 문장
~~~

상태: 구현 완료. 질문은행 데이터 변경은 별도 관리한다.

### Phase 3 — Audio + STT

~~~text
질문별 녹음 → WAV → CLOVA STT → transcript
→ 발화시간·발화속도·무음·긴 무음 계산
~~~

상태: 브라우저 코드와 단위 테스트 완료. 실제 장치 E2E는 별도 확인이 필요하다.

### Phase 4 — Vision

~~~text
Face Landmarker → 시선 좌표 → Heatmap → 평균 → 표준편차
~~~

상태: 질문별 결과 화면 및 empty/invalid frame 처리를 포함해 구현 완료.

### Phase 5 — 답변 내용 LLM 확인

~~~text
질문 + transcript + 프로필
→ LLM
→ good / partial / off_topic / insufficient
~~~

상태: 구현 완료. reason과 missing_points만 반환하고 follow-up과 숫자 점수는 사용하지 않는다.

### Phase 6 — 결과 화면 통합

상태: 질문별 내용·음성·시선과 세션 평균 측정값을 통합 완료.

### Phase 7 — E2E 테스트

~~~text
프로필 입력 → 질문 Random Pick → 개인화 → 답변
→ STT → 시선/음성 측정 → LLM 내용 확인 → 결과 화면
~~~

상태: 정적·단위·production build 검증 완료. 카메라·마이크 권한을 포함한 실제 브라우저 E2E는 장치 환경에서 남아 있다.

---

## 14. 코드 원칙

1. 현재 저장소 구조와 기존 STT/면접 흐름을 우선한다.
2. 불필요한 대규모 refactor를 하지 않는다.
3. LLM prompt와 API 호출 코드를 UI에서 분리한다.
4. Vision/Audio feature 계산을 UI 코드와 분리한다.
5. API key는 .env에서 읽고 커밋하지 않는다.
6. LLM JSON은 Pydantic으로 validation한다.
7. LLM 실패 시 전체 면접이 종료되지 않도록 원문·측정값 fallback을 사용한다.
8. 질문마다 모델을 새로 load하지 않는다.
9. raw audio/video는 영구 저장하지 않고 결과에 필요한 요약값만 전송한다.
10. 질문은행 데이터와 런타임 코드를 분리한다.

## 16. Definition of Done

### Track A

- [ ] 자기소개서를 입력할 수 있다.
- [ ] 주장과 경험을 LLM이 분리한다.
- [ ] 경험별 위험도와 약점을 반환한다.
- [ ] 예상 질문을 반환한다.

### Track B

- [x] 항목별 Random Pick이 동작한다.
- [x] 질문이 프로필 기반으로 개인화된다.
- [x] 개인화 실패 시 원문 질문을 사용한다.
- [x] 질문별 STT 요청 흐름이 연결돼 있다.
- [x] 발화 속도와 답변/발화 시간이 출력된다.
- [x] 무음 시간·비율·긴 무음 횟수가 출력된다.
- [x] 시선 Heatmap이 출력된다.
- [x] 시선 평균·표준편차·유효 프레임 비율이 출력된다.
- [x] LLM이 답변 내용 상태·이유·빠진 내용을 반환한다.
- [x] Vision/Audio에 점수를 부여하지 않는다.
- [x] 최종 결과 화면에서 질문별 결과와 세션 평균을 확인한다.
- [ ] 실제 카메라·마이크 권한을 포함한 전체 E2E를 장치에서 완주한다.

~~~text
InterReview는 자기소개서의 면접 취약점을 LLM으로 분석하고,
질문은행 기반 개인화 면접에서 답변 내용은 LLM으로 확인하며,
~~~
